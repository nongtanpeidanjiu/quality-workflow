# quality-workflow

**把质量管理体系装进 AI 智能体：先弄清要什么，决定结果的东西先验证再使用，做完逐项核对证据，交付时实话实说。**

写文档、改制度、做统计、查资料、写代码，不限于某一类工作。

| 平台 | 支持情况 | 安装 |
|---|---|---|
| WorkBuddy 桌面版（Mac、Windows） | 支持。Mac 和 Windows 都实测过 | 见下文“安装” |
| ChatGPT 桌面版的 Codex 模式（Mac、Windows） | 支持。Mac 实测过；**Windows 按官方文档编写，没有在真机上测试过** | 见 [Codex 版安装说明](docs/codex/安装说明.md) |

ChatGPT 桌面版的 Work 模式和 Chat 模式不支持：前者在云端运行，官方不支持在那里运行插件的钩子；后者不操作你电脑上的文件。

## 为什么要做这个

### 智能体出错，往往不是因为不够聪明

用 AI 智能体干活，最怕的不是它做不出来，而是它**做得很漂亮，结果却是错的**：

- 你说“统计一下投诉率”，它没发现数据只导出了半个季度，算出一份工整的报告。
- 你说“按新制度改手册”，项目里新旧两份制度，它拿了旧的那份。
- 你说“写个产品介绍”，它没问给谁看，资料里没有的卖点也顺手编了进去。
- 你说“改一下”，它把旁边不该动的也“优化”了。
- 它说“已完成”，其实什么都没核对过。

这些问题有一个共同点：**一项数据错了，方法和过程再漂亮，结果也不可能正确；对你的意思理解错了，也是一样。** 而智能体恰恰不区分轻重：决定结果对错的东西，和无关紧要的措辞，它用同样的力气对待。

### 写进提示词，管不住

把规则写进提示词，一开始有用，对话一长、任务一急就被跳过。写成全大写、加上“必须”，也改变不了。规则没有被执行的保障，就等于没有规则。

## 设计思路：借鉴质量管理体系

制造业、医疗器械这些行业，几十年前就遇到了同样的问题：怎样让一群能力参差、记忆有限的人，稳定地交付正确的结果？答案是质量管理体系。它不靠个人的自觉和发挥，而靠一套被验证过的机制。

这个插件把质量管理体系最核心的几条思路，改造成了智能体能执行、程序能把关的规则：

| 质量管理的思路 | 在插件里变成了什么 |
|---|---|
| **基于风险的思维**：力气花在出错影响最大的地方 | 不给任务笼统分级，而是找出“决定结果的东西”，只对它们从严 |
| **先确认需求，再策划过程** | 开工前先复述理解和步骤，你确认了才动手 |
| **进货检验**：原料不合格，后面怎么加工都没用 | 你给的数据和资料，使用前先检验是否完整、一致、现行 |
| **过程控制**：在关键工序设检验点，不等最后才查 | 决定结果的东西在被使用之前就要验证，中间成果也一样 |
| **验证与确认分开**：做得对不对，和是不是你要的，是两件事 | 能客观核对的由智能体核对并留证据；只有你知道答案的由你确认 |
| **以证据为基础的决策** | 每一项验证都要有证据文件；自己再读一遍觉得没问题，不算验证 |
| **独立检验** | 独立检查员只能看不能改，逐项核对证据是否成立 |
| **变更控制** | 改需求要记录原话、分析影响、重新确认；小改动走轻流程，动了关键项才重新验证 |
| **可追溯** | 你的原话、每一项的验证证据、每次变更，都留在本地的任务记录里 |

它不是让模型更聪明，而是让它**像一个受过训练的质量工程师那样工作**。

## 它怎么工作

### 1. 找出决定结果的东西

接到任务，先问一个问题：**这件事的结果由哪些东西决定？其中哪一样错了，结果必然错？**

通常是这几类：对你意思的理解、你给的数据和文件、引用的规定和外部事实、计算的口径和方法。这些是“决定性的项”，必须先验证再使用。其余的，措辞、版式、顺序，正常做好即可。

**例子：** 统计上季度各产品的投诉率。

| 决定结果的东西 | 错了会怎样 | 谁来验证 | 怎么验证 |
|---|---|---|---|
| 结果给谁用、用来做什么 | 整份结果用不上 | 你 | 它复述，你确认 |
| 投诉数据是否完整 | 结果必错 | 智能体 | 检查条数、日期范围、重复和异常 |
| 投诉率的分母取销量还是在用量 | 结果必错 | 你 | 它列出选项和推荐，你来定 |
| 计算结果 | 结论必错 | 智能体 | 换一种方法重算，两次一致 |
| 图表用什么样式 | 只影响阅读 | — | 不单独确认 |

### 2. 开工前先复述，你确认了才动手

稍大一点的事，它的第一条回复只有几行：它理解你要做成什么、打算分哪几步、最多一个方向性的问题。你回一句，它才往下走。

理解错了，后面做得再好也是白做。这一步就是在花力气之前把方向对准。改错别字、把一列数加起来这类小事，它直接做，不会多问。

### 3. 你给的资料，先检验再用

是不是该用的那一份、是否完整、前后有没有矛盾、有没有明显异常、是不是现行有效的版本。发现问题先告诉你，由你决定怎么办，不会悄悄删数据、补数据或换个算法绕过去。没问题的资料直接采用，不会让你把自己给的东西逐项再确认一遍。

### 4. 只有你能定的事，集中问一次

口径怎么选、两份文件用哪一份、资料互相矛盾时以哪个为准。它会集中起来问，每个都带选项和推荐，你可以直接点选。检验后没有需要你定的事，它就不再打扰你。

### 5. 验证要对症，证据要留下

| 要验证的 | 方法 |
|---|---|
| 对你意思的理解 | 复述加一个具体例子；先给大纲或小样 |
| 数据 | 回到原始文件核对条数、范围、异常 |
| 规定和外部事实 | 回到官网或一手来源核对原文和版本；查不到的两个独立来源交叉核对 |
| 计算 | 换一种方法重算 |

每一项验证都要写成证据文件。证据在验证之后被改动，这次验证自动作废。核对不了的东西，它会明确告诉你“这一项没法核对”，由你决定继续用、换办法，还是自己去核实。

### 6. 做完由独立检查员逐项核对

检查员是另一个智能体，**只能看，不能改**。它做两件事：开工前检查“决定结果的东西”有没有漏项；交付前逐项核对每一项的证据是否成立、成果里用的是不是验证过的那一版。少核对一项，程序不放行。

### 7. 改动分轻重

做完后只改一句措辞，它改完核对一下就交付，不会把整套检查重走一遍。动到了数据、口径或结论，才重新验证受影响的部分。目标、范围或完成标准变了，必须拿到你新的回复才能继续。

### 8. 交付时实话实说

完成了什么、每一项是怎么验证的、由谁验证的、哪些没法核对、哪些需要你决定。“已写完”“已验证”“已确认”是三种不同的状态，不会混着说。

## 程序把关，不只是提示词

下面这些规则由插件里的程序在智能体每次写文件、执行命令、准备结束时自动检查。智能体想绕也绕不过去：

| 关卡 | 效果 |
|---|---|
| 写文件之前先表态 | 要么声明“这是小事”并说明理由，要么复述理解、等你回复。都没做，写不了 |
| 确认之前不动成果 | 你确认之前，只能写计划、小样和检验记录 |
| 不能越界 | 只能改说好的范围 |
| 不覆盖你的改动 | 你手动改过的文件，它再写之前会被拦下 |
| 先验证、后使用 | 决定结果的东西没有验证记录，用到它的步骤不能开始 |
| 没验证完不能交付 | 决定结果的东西没有全部验证、没通过独立检查，任务不能结束 |
| 证据不能事后改 | 证据在验证后被改动，验证自动作废 |
| 检查要逐项 | 检查报告必须对每一项给出结论，缺一项不接受 |
| 确认必须是你的原话 | 程序核对确认记录确实是你说过的完整的话，不能从“我不同意”里截出“同意” |
| 变更要重新确认 | 需求变了，必须有你新的回复，不能拿之前的话当同意 |
| 难以收回的动作先问你 | 删除数据、对外发布、强制推送，执行前弹出确认 |

## 实际效果

在真实的 WorkBuddy 里，准备了五个埋了问题的任务，覆盖数据统计、按制度改文档、写介绍、小改动和小计算：

| 任务 | 埋的问题 | 表现 |
|---|---|---|
| 统计投诉率 | 数据只导出到 9 月 15 日；4 条重复记录；产品名写法不一致；分母有两种取法 | 动手算之前全部指出；分母交给用户定；三种方法交叉重算，数字全部正确 |
| 按新制度改手册 | 项目里新旧两份制度；新制度里同一标准写了 600 和 550 两个数；范围外有个错别字 | 发现旧制度已废止；指出矛盾并请用户裁定；错别字只报告不擅自改；用户中途改主意后先说明范围变化再改；逐行比对证明只动了该动的地方 |
| 写产品介绍 | 没说给谁看；资料里的注册证号是占位符 | 先问受众、先给大纲；指出证号是占位符且格式与产品类别不符；不编造资料里没有的价格 |
| 改错别字 | 无 | 直接改完，没有多余的流程 |
| 求和 | 一行数量写成“1,200”；一行数量为空 | 结果正确；两处都主动提醒 |

**埋的问题全部被发现，结果全部正确，小事没有被流程拖累。**

这五个测试项目和评分参考都在 [`examples/`](examples/) 里，你可以自己跑一遍。

## 安装

下面是 WorkBuddy 版的安装方法。**Codex 版**见本节末尾。

1. 从 [Releases](../../releases) 下载 `quality-workflow-0.4.0.zip`。
2. 在 WorkBuddy 里新建一个任务，把压缩包拖进对话框，发送：

```
帮我安装这个插件，按压缩包里《给智能体的安装步骤》做。
```

3. 看到“安装成功”后，完全退出并重新打开 WorkBuddy，新建一个任务，随便发一句话，按提示完成安装自检。

**Windows 用户请多做一步：** 重新打开 WorkBuddy 后，先到“专家·技能·连接器 → 技能 → 套件”里找到 quality-workflow，确认开关是打开的；没有打开就手动打开，再重启一次 WorkBuddy。Windows 上 WorkBuddy 运行时会占用设置文件，启用状态有可能没写进去，插件装上了却不生效。新任务里出现了安装自检的提醒，才说明插件真的生效了。

**以后自动更新。** 安装时会从 GitHub 安装，并打开 WorkBuddy 自带的市场自动更新：WorkBuddy 每次启动会检查一次（每天最多一次），有新版本就在后台下载，下次重启后生效。电脑连不上 GitHub 时，会改用压缩包里的文件安装，这种情况下不会自动更新，但插件会在新任务里提醒有新版本，说“更新插件”即可升级。

电脑上没有 Python 也没关系，安装时会自动装一份免安装版，不改系统设置，不需要管理员权限。旧版本会被自动卸载。

手动安装、更新和卸载，见 [安装说明](docs/安装说明.md)。

### Codex 版（ChatGPT 桌面版的 Codex 模式）

1. 从 [Releases](../../releases) 下载 `quality-workflow-codex-0.4.0.zip`。
2. 在 ChatGPT 桌面版的 Codex 里新建一个任务，把压缩包拖进对话框，发送：

```
帮我安装这个插件，按压缩包里《给智能体的安装步骤》做。
```

3. 看到“安装成功”后，完全退出并重新打开 ChatGPT 桌面版，到 **Settings > Hooks** 里把 **Quality Workflow** 的钩子全部信任并打开，再新建任务完成安装自检。

电脑上不需要预先装任何东西：没有 Python 会自动装一份免安装版，不需要 git 和 Node。

和 WorkBuddy 版有三点不同，都是 Codex 平台的规定决定的：

- **钩子要你手动信任，** 插件每次更新后还要重新信任。没信任时，智能体会在开工前检查出来并停下，不会在关卡失效的情况下干活。
- **不在后台自动更新。** 有新版本时提醒你，你说“更新插件”才更新。
- **难以收回的动作没有弹窗。** 程序会先拒绝，智能体把后果告诉你，你同意后再执行一次才放行。

详见 [Codex 版安装说明](docs/codex/安装说明.md)。

## 使用建议

- **说清楚给谁用、用来做什么，** 它问得就少，做得也更准。
- **认真看它的复述，** 这是你把关最重要的一次机会。
- **它列出的“重点核对的东西”，你可以增删。** 哪些东西决定结果，往往你最清楚。
- 任务记录只保存在你自己电脑上的 `.flow` 文件夹里，插件不上传任何内容。

## 目录

| 目录 | 内容 |
|---|---|
| [`plugin/`](plugin/) | WorkBuddy 版插件源码：流程说明、独立检查员、程序关卡、自动测试 |
| [`codex/`](codex/) | Codex 版插件。流程脚本和关卡程序与 WorkBuddy 版共用同一份源码，由 `tools/sync_codex.py` 同步 |
| [`docs/`](docs/) | [设计规格](docs/设计规格.md)、安装说明、快速安装、升级说明 |
| [`installer/`](installer/) | 一键安装脚本、打包脚本。Codex 版在 `installer/codex/` |
| [`tests/`](tests/) | Codex 版的自动测试 |
| [`examples/`](examples/) | 五个埋了问题的测试项目、测试说明、评分参考 |

运行自动测试：

```bash
cd plugin && python3 -m unittest discover -s tests -p 'test_*.py'
```

Codex 版的自动测试，以及改了 `plugin/` 下的共用文件后同步到 Codex 版：

```bash
python3 -m unittest discover -s tests -p 'test_*.py'
```

```bash
python3 tools/sync_codex.py
```

打包安装包（生成在 `dist/`），Codex 版用 `installer/codex/打包.py`：

```bash
python3 installer/打包.py
```
