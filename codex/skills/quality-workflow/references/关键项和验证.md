# 关键项和验证

## 怎么找关键项

清单要短。只列真正决定结果的，一个任务通常三到六项决定性的项。同一份资料里的多个数值算一项，不要一个数一项。

问自己三个问题：

1. **这个结果是从哪些东西得出来的？** 数据、原文件、引用的规定、用的方法、作出的假设。
2. **其中哪一项错了，结果必然错？** 这些是决定性的。
3. **我对用户意思的理解，有哪几处一旦理解错，整份结果就用不上？** 目的、给谁用、成功标准，至少有一项是决定性的。

各类任务常见的决定性项（只是提示，不是完整清单）：

| 任务类型 | 常见的决定性项 |
|---|---|
| 写或改文档 | 读者和用途、必须保留的内容、引用的事实和条款、结构（提纲） |
| 改代码 | 现有哪些行为不能变、问题的真正原因、运行环境、怎么算修好 |
| 调研 | 用来做什么决定、信息来源、时效、比较的口径 |
| 数据处理 | 数据是否完整、口径、异常值怎么处理、计算方法 |
| 设计 | 使用者和场景、不能变的约束 |

例子（统计上季度各产品的投诉率）：

| 编号 | 要素 | 类型 | 错了会怎样 | 级别 | 谁验证 | 怎么验证 |
|---|---|---|---|---|---|---|
| K1 | 结果给质量例会用，用来决定先整改哪个产品 | 理解 | 整份结果用不上 | 决定性 | 用户 | 复述后请用户确认 |
| K2 | 投诉数据是上季度的全量数据 | 输入 | 结果必错 | 决定性 | 用户 | 核对条数和起止日期后，请用户确认是不是全量 |
| K3 | 数据没有缺失、重复和明显异常 | 输入 | 结果必错 | 决定性 | 智能体 | 输入检验 |
| K4 | 投诉率的分母取同期销量 | 方法 | 结果必错 | 决定性 | 用户 | 列出几种口径，由用户选定 |
| K5 | 各产品投诉率的计算结果 | 中间成果 | 结论必错 | 决定性 | 智能体 | 换一种方法重算，两次一致 |
| K6 | 产品按产品线分类 | 方法 | 部分结果错 | 重要 | | |

同一批数据可以拆成两项：是不是全量只有用户知道，有没有缺失和异常可以客观核对。

## 验证方法要对症

| 类型 | 验证方法 | 证据 |
|---|---|---|
| 理解 | 复述加一个具体例子；给骨架（大纲、草图、要点）或小样；用户确认 | 用户原话 |
| 输入 | 输入检验（见下）；是不是全量、是不是这一份，问用户 | 检验记录、用户原话 |
| 依据 | 回到官网或一手来源核对原文和现行版本；官网没有的，两个相互独立的来源交叉核对 | 链接、原文位置、查询日期 |
| 方法 | 口径和取舍由用户确认；计算换一种方法重算，或用已知结果的小例子验算 | 用户原话、重算记录 |
| 假设 | 影响结果的假设交用户确认 | 用户原话 |
| 中间成果 | 对照判定标准检查；数字逐个追溯到来源 | 检查记录、追溯关系 |

**不算验证：** 自己再读一遍觉得没问题；凭记忆认为“应该是这样”；只是把同样的计算再跑一遍。

## 输入检验

拿到的数据和资料，使用前先检验。用户给的也要检验：用户可能给错文件、给了旧版，或者数据本身有缺。

**用户提供的资料默认可以作为依据，检验通过就算验证完。** “拿这份资料核它自己不算验证”这种想法不对：用户给你资料，就是让你用它。你要查的是它有没有问题，不是让用户再担保一遍。所以：

- 资料里的数值、事实，照用，交付时写明出处。不要把“参数的真值”列成要用户逐项确认的项。
- 只有三种情况才问用户：检验发现了疑点；“是不是全量”“是不是这一版”这类只有用户知道的事；资料之间互相矛盾。
- 资料里明显是占位或示例的内容（如“XXXX”“示例”），指出来，问用户怎么处理。

| 检验项 | 查什么 |
|---|---|
| 是不是要用的那一份 | 文件名、版本、日期、时间范围和任务对得上 |
| 完整性 | 条数、页数、章节是否齐全；有没有截断、缺失的时间段 |
| 一致性 | 口径、单位、分类前后一致；内部有没有自相矛盾 |
| 异常 | 空值、重复、明显不合理的值 |
| 适用性 | 是不是现行有效的；适不适合这个任务的用途 |

- 检验结果写进证据文件：查了什么，发现了什么。
- **发现问题先报告，** 说明问题和可选的处理办法，由用户决定。不悄悄删数据、补数据或换口径。
- 检验不了的部分要明说。
- 输入是决定性的项时，检验通过，或用户已知情并作出决定，才算验证完。用户作出决定的，用用户原话记录。

## 证据怎么写

证据是 `evidence/` 目录下的一个文件，让没参与的人也能看懂这一项为什么算验证过了：

```
关键项：K3 数据没有缺失、重复和明显异常
核对了什么：complaints.csv
怎么核对的：统计行数、按月分布、按编号查重、数值范围
结果：共 1,284 行；7、8、9 月分别 412、455、417 行；无重复编号；无空值
（附命令输出或关键片段）
结论：成立
```

- 一项一份证据最清楚。一份证据确实同时支持几项时可以共用。
- 依据类的证据写明链接、版本或发布日期、查询日期、原文所在位置和原文片段。
- 证据记录后不要再改。要补充就写新文件，重新 `qflow item verify`。

## 核对不了的时候

查不到一手来源、数据来源说不清、无法重算时：

1. 明确告诉用户：这一项是什么，为什么核对不了，试过什么。
2. 给出选项：继续使用（成果会标明这一项未验证）、换一个方案、由用户自己核实后告知。
3. 用户同意继续：`qflow item waive <编号> --quote 用户原话`。交付时必须声明，成果要由用户确认。

不能把核对不了的东西当作已验证使用。

## 关键项会变

- 做的过程中发现新的关键项：补进任务单的清单，`qflow change --note 说明`，验证后再继续用它。
- 关键项的内容变了（比如口径改了）：改任务单，`qflow change`。这一项要重新验证，用到它的步骤会被标为需复核。
- 发现某一项验证得不对：`qflow item recheck <编号> --reason 原因`。
- 降低级别或删掉决定性的项：要用户同意，`qflow change --note 说明 --quote 用户原话`。
