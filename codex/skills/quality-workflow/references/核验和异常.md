# 核验和异常

## 独立检查

检查员做两件事：

- **说定前，检查关键项清单（类型：清单）。** 有没有漏掉的决定性的项，有没有级别定低的，对用户意思的理解还有哪些歧义。
- **交付前，逐项核证据（类型：交付）。** 每个决定性的项的证据是否真能支持“已验证”；成果里的数字、事实、引用能否追到已验证的关键项；有没有清单之外、未经验证的决定性内容混进来。

规则：

- 只给检查员任务单路径、成果位置和检查类型，不给你的解释。
- 报告由系统保存到 `evidence/`。你不能自己判定通过。系统没有保存时，要告诉用户，并经用户同意后用 `qflow check --report <路径> --quote 原话` 记录。
- 成果、确认页或关键项的验证变化后，之前的通过结论自动失效。按小改动（`--light`）登记的改动除外，见 [资料和变更](资料和变更.md) 的“改动分轻重”。
- 清单检查的结论不是“通过”时，改好后要再查一次，通过了才能往下走。
- **不要一轮接一轮地查。** 检查员提的“建议”只记录，不必为它返工再查。重新检查时告诉检查员上次查过什么、这次改了什么，让它只查改动和受影响的部分。
- 交付检查的报告必须逐项列出每个决定性的项的结论，缺一项脚本不接受。
- 检查员判某个决定性的项“不成立”时，这一项会退回待验证。回到这一项重新验证，不在下游打补丁。
- 检查员和你是同类模型，可能有相同的盲点。所以答案在用户那里的项必须由用户确认，核对不了的项必须交用户决定。

## 问题处理

| 级别 | 含义 | 可选去向 |
|---|---|---|
| 阻断 | 决定性的项验证不成立；错误、违反要求、影响使用 | 修复，或交用户决定 |
| 重要 | 影响质量但不至于错 | 修复；不修要由用户决定（延后或交用户决定） |
| 建议 | 可以更好 | 修复或只记录 |

```
qflow issue add --level 阻断 --text 问题
qflow issue route --id Q1 --disposition 修复
qflow issue bounce --id Q1      # 这个问题又被退回
```

- **作者不同意：** 写明理由，再开一个新的检查员实例，不看第一份报告，独立判断；或由用户裁定。
- **用户接受已知问题：** 先有一次交付检查，再 `qflow check --user-ruling --issues Q1 --quote 原话`。交付时标明“用户接受已知问题”。
- **同一问题退回 2 次仍未解决：** 脚本把任务转为受阻。交给用户，说明问题、试过什么、可能根因和可选方案。
- **第二次检查仍有新的阻断问题：** 回到根因所在的关键项或步骤，不再打补丁。

## 无法检查时

查不了或检查员弃权时，告诉用户：

- **用户裁定通过：** 见上。
- **用户同意标为未核验：** `qflow close --unverified --quote 原话`。交付时声明“未经独立核验”。
- **某个决定性的项核对不了：** 这和检查员查不了是两回事，见 [关键项和验证](关键项和验证.md) 的“核对不了的时候”。

## 异常

总原则：先停止扩大影响，再如实说明，最后按根因处理。

| 异常 | 处理方式 | 不允许 |
|---|---|---|
| 决定性的项验证不通过 | 停下，报告问题和可选办法，由用户决定 | 悄悄修数据、换口径或绕过 |
| 决定性的项核对不了 | 告诉用户，由用户决定后用 `qflow item waive` | 当作已验证使用 |
| 做到一半发现漏了关键项 | 补入清单，验证后再继续；已用到它的成果重新核对 | 当作没发现 |
| 中断或换智能体接手 | 按下面的接续步骤恢复 | 靠聊天摘要猜进度 |
| 发现上游有错 | `qflow item recheck <编号> --reason 原因`，回到那一项重新验证；用到它的步骤会被标为需复核 | 只在当前步骤打补丁 |
| 发现范围外的问题 | 记录并报告，由用户决定 | 顺手修改 |
| 自己改错或越界 | 立即停止，说明情况，能用基线恢复就恢复，不可逆的交给用户 | 隐瞒或悄悄改回 |
| 工具失败、没权限、网络不通 | 有限重试，然后说明情况；换方法也要声明 | 绕过权限或假装完成 |
| 目标无法实现 | 尽早说明原因和替代方案 | 悄悄交一个缩水版 |
| 上下文或额度快用完 | 在步骤边界保存状态并交接 | 赶工、跳过验证、减少阅读 |
| 等资料或决定 | `qflow state 受阻 --reason 原因`，处理后 `qflow state 恢复 --reason 原因` | 硬做 |
| 多个智能体同时工作 | 同一文件只有一位维护者 | 同时写同一文件 |
| 任务单和用户确认的不一致 | `qflow change`，必要时退回待确认 | 悄悄继续 |

## 接续步骤

1. `qflow status`，读任务单。
2. `qflow fingerprint scan`，看有没有外部改动。
3. 看关键项：哪些已验证，哪些还没有。
4. 把“进行中”的步骤视为未完成，检查实际成果。
5. 用几句话复述当前情况，然后继续。

没有建档的任务没有文件，中断后只能靠成果本身接续。

## 记录问题

用户纠正或任务出问题时，把问题、是哪个关键项没列出、没问到或验证方法不对，以及本来可以怎么发现，追加到 `~/.quality-workflow/improvements.md`。任务进行中不得自行修改方法，由用户定期决定是否改进。
