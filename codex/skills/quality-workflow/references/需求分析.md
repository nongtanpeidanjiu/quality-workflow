# 需求分析

**对用户意思的理解永远是决定性的关键项：理解错了，后面做得再好，结果也是错的。**

人很难凭空描述需求，但看到具体的东西，很容易说出“不是这样”。目标不是证明需求完整，而是尽早暴露理解偏差，让跑偏的代价足够小。

## 需求分四层

| 层次 | 含义 | 怎么得到 |
|---|---|---|
| 明示需求 | 用户说出来的 | 记下原话，避免被改写 |
| 隐含需求 | 用户默认理应如此，不会特意说 | 从项目、文件和行业惯例推断，写成假设 |
| 必须履行 | 法规、合同、公司规定 | 查资料，或向用户要 |
| 真正目的 | 为什么做，给谁用，用来做什么 | 从上下文推断，并向用户确认 |

## 识别没说清的信号

| 信号 | 例子 | 处理 |
|---|---|---|
| 模糊词 | “优化”“专业”“简单一点” | 拆成可判定的含义，让用户选 |
| 直接给方案 | “加一个导出按钮” | 问它要解决什么问题 |
| 缺对象 | 没说给谁用、用在什么场合 | 先从上下文推断，再确认 |
| 没说不能动什么 | “把这个文件改一下” | 主动列出可能受影响的部分 |
| 前后矛盾 | “要全面，但不能超过一页” | 指出矛盾，让用户定优先级 |
| 用词有专业含义 | 用户所在行业里，一个词有特定意思，和你习惯的理解不同 | 用一个具体例子复述，确认是不是这个意思 |

## 要弄清的维度

影响结果对错的，登记为“理解”类的关键项（决定性或重要）；不影响的不用登记。

| 维度 | 要弄清什么 |
|---|---|
| 目的 | 为什么做，拿到结果后接下来要做什么 |
| 使用者和场景 | 给谁用，用在什么场合 |
| 范围 | 要做什么，不做什么，不能动什么 |
| 约束 | 必须满足的规定、时间、格式、环境 |
| 风格和偏好 | 语气、详略、外观、有没有好的参照 |
| 成功标准 | 怎样算完成，反例是什么 |

风格和偏好最容易漏掉。影响结果时要明确询问，并尽量用小样校准。

| 任务类型 | 补充重点 |
|---|---|
| 写或改文档 | 读者、用途、格式、必须保留的内容 |
| 改代码 | 现有哪些行为不能变、运行环境、怎么验证 |
| 调研 | 用来做什么决定、时效要求、来源要求、深度 |
| 数据处理 | 口径、异常值怎么处理、结果给谁看 |
| 设计 | 使用者、使用场景、不能变的约束 |

先根据项目资料自己回答，只把答不上来的问用户。

## 怎么问

1. **先调查，后提问。** 能查到的不问。
2. **用复述加例子代替填空。** 如“我理解你要 X，给 Y 用，不动 Z。比如遇到某种情况，我会这样处理。对吗”。
3. **优先问决定性的、把握小的。** 每得到一个答案就重新排序。用户说“这个不需要”，相关分支不再问。
4. **关键问题一次一个。** 带推荐答案和原因，后面的问题根据前面的回答调整。
5. **只问会改变做法的问题。** 允许回答“你来定”。
6. **把假设摆出来。** 让用户一眼能发现不对。
7. **成果先给骨架。** 文档先给大纲，设计先给草图，方案先给要点。骨架确认后再展开，不要直接写完整篇。
8. **用小样校准。** 先做一页样张或一节内容，放在 `drafts/`。
9. **答案立即写回任务单。** 发生矛盾时替换旧内容，旧值只留在变更记录里。
10. **已决定的不重复问。**

**问多少：** 决定性的项，答案在用户那里的都要确认，不设上限，但要集中、带推荐。重要的项不问，写明采用的做法，用户可以纠正。一般的项不问。

用户答不上抽象问题时，换一种问法：

| 方法 | 不要这样问 | 改为这样问 |
|---|---|---|
| 还原场景 | 你的需求是什么？ | 上次遇到这个问题时，具体发生了什么？ |
| 二选一 | 你想要什么风格？ | 更像 A（详细的操作步骤）还是 B（一页的要点）？ |
| 反向提问 | 你的标准是什么？ | 什么样的结果你一看就不满意？ |
| 找参照 | 要做到什么程度？ | 有没有你觉得好的例子？ |
| 追问用途 | 需要哪些内容？ | 拿到结果后，你接下来要做什么？ |

**假设模式：** 用户明显答不上来，或希望少回答时，先读资料，写出“我的假设和把握度”，让用户只纠正不对的地方。

## 好坏对比

**用户：** 帮我优化一下这份报告。

差：好的，我来优化。（直接大改语言和结构。）

差：请问你的目标、读者、风格、长度、格式分别是什么？

好：我读了报告，它的结论在第 5 页才出现。我猜这份报告要给管理层看，所以“优化”是让结论更靠前、更短。是这样吗？如果是别的目的，比如改错或给技术同事看，做法会不同。

**用户：** 加一个导出按钮。

差：直接加一个导出 CSV 的按钮。

好：加按钮不难。先确认一下：导出后要拿去做什么？如果是发给财务核对，可能需要固定的列和格式；如果只是备份，全量导出就够了。我的推荐是先做 CSV，你看对吗？

**用户：** 我觉得你的风险判定不对。

差：好的，我重新设计一套风险判定。（没弄清哪里不对就重做。）

好：我先确认一下你的意思。你是说判定的角度不对吗？比如一份数据如果错了，后面怎么做结果都是错的，所以数据本身就该重点管，而不是看这个任务有没有人依赖？如果是这个意思，我要改的是判定标准，不只是分几档。

**用户：** 帮我写个项目介绍。

差：直接写完整篇，被否定后换个写法再写一整篇。

好：先给大纲：写给谁看、按什么结构展开、重点突出哪几点。用户确认大纲后再写正文。

## 用户说“不对”时

立刻停下，不接着修补，也不换个写法再做一遍。先弄清是哪一项理解错了或漏了，用自己的话加一个例子复述给用户，确认后更新关键项清单，再继续。

## 请用户确认前

- 能写出可判定的成功标准。
- 能举出一个“看似满足，其实不是用户要的”反例，并和确认页一起确认。
- 假设都已列出。
- 剩下的未知项都不是决定性的。

## 边界

- **潜在需求只提议，不自动做。**
- **用户说“你看着办”时不追问不休：** 按推荐方案推进，写明假设，优先选容易恢复的做法。这句话本身可以作为用户对相关项的确认来引用。难以收回的动作仍要确认。
- **理解贯穿全程：** 用户的每次纠正都写回任务单，并更新关键项清单。
